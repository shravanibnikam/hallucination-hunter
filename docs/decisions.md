# Decisions

- Use a server-only PostgreSQL driver with Supabase's transaction pooler, rather than a browser Supabase client. This allows atomic round creation and locked guess writes.
- Use a system font stack so builds and play never need font downloads.
- Use local PostgreSQL for repeatable database verification. Production uses Supabase Free; no additional hosted services are required.
- The six ordinary samples plus two attention checks form eight CSV rows. Samples are demonstrations, not a validated research dataset.
- Dataset rows require stable UUIDs for safe, repeatable upserts. Omitted optional CSV values use database defaults; importing an existing pair cannot change its content once a round references it (use a new UUID for revisions).
- Pin TypeScript to major version 6 because the current Next.js ESLint parser rejects TypeScript 7. Next.js itself uses the latest stable release.
- Pin ESLint to major version 9; the React plugin currently bundled by eslint-config-next uses APIs removed in ESLint 10.
- Without any attention-check pair, keep the specified N−1 ordinary items and shorten the round by one (up to 9). If the pool is empty, return a friendly 503 rather than creating an empty session.
- The random session UUID is an anonymous bearer capability, kept only in sessionStorage. A minimal GET session endpoint returns progress for refresh recovery; it exposes no item IDs or answer metadata. No cookies are needed.
- Refresh resumes at the next unguessed item; an unsubmitted answer is discarded. The timer restarts on render, while the first served_at stays unchanged. A submitted guess is never rewritten.
- Viewport widths below 768px are recorded as mobile; all others are desktop. This is a coarse screen classification, not user-agent collection.
- Scores and streaks include all round items. Category accuracy, mean confidence, and calibration exclude attention checks. Calibration thresholds use unrounded values; displayed percentages round to the nearest integer. An attention-only round gets an explicit insufficient-data insight.
- Keep all app and share-image color, radius, and type tokens in lib/design-tokens.ts, exposed to Tailwind through CSS variables.
- Shared scores are bounded but self-reported; they never fetch or identify a session. A single next/og image route varies by score and total.
- Nicknames are optional public aliases. Raw research exports are private working files: remove aliases and coarsen timestamps before any anonymized publication. Hosting providers may process operational connection metadata outside the app's study data.
- In-memory limits avoid IP collection entirely: 60 session creations/minute per process, 600 guess requests/minute per process, and 30/minute per session. They reset on cold starts and do not coordinate across Vercel instances; shared global budgets can affect other players. This is a basic abuse brake, not distributed bot prevention. Maps are bounded and expire during requests; no jobs or paid storage are needed.
- Integration tests require a separate database name ending in _test and reset that database's study tables. Playwright uses the same disposable database and real random assignment, retrying session creation until each condition is covered; no production condition override exists.
- A round without an attention check has no failed check, but does not qualify for the leaderboard: eligibility requires an actual correctly answered attention item.
- The reveal highlights the first exact occurrence of fabricated_span. Dataset authors should use an unambiguous span when repeated wording could confuse readers.
- Rounds balance ordinary items by `hallucination_type` before category. The four named types (`wrong_number`, `wrong_entity`, `wrong_date`, `invented_citation`) each get 2 of the 9 ordinary slots and one randomly chosen type gets the extra (3, 2, 2, 2). The one-third category cap is secondary: when the pool cannot satisfy both, the cap rises only as far as type balance requires. `other` pairs fill only slots the four types cannot, and a short type's slots are dealt round-robin to the others. Within these rules the least-shown pair is taken greedily unless it would make the remaining quotas impossible (checked exactly with Hall's condition), so exposure balance is approximate rather than optimal. The type never leaves the server before a guess.
- Single rounds show the fake answer on exactly half of the ordinary items, rounding a 9-item round to 4 or 5 at random per round, at random positions; the attention check is always shown fake. A shorter round with an even count shows exactly half (the six-item sample round shows 3). Paired rounds still place the fake left or right independently per item.
- Repeat play is marked by a random UUID kept in `localStorage` under `hh_device_id` and stored in nullable, indexed `sessions.device_id`. It is created with `crypto.randomUUID()` on first start, replaced if malformed, and sent as null when storage or `randomUUID` is unavailable. It is never returned by any API or shown publicly. Exports add `device_id` and `device_round_number` (1 for the browser's first session by creation time, counting all sessions including pilot and non-study ones; empty without an ID). It identifies a browser profile, not a person: clearing data, another browser, or a private window starts over.
- Every pair stores `real_span`, and `answer_fake` must be `answer_real` with its single occurrence of `real_span` (overlapping matches count as repeats) replaced by a different `fabricated_span`. The importer reports violations by CSV line and `pairs_real_span_check` enforces the same rule. Attention checks are one-span swaps too (for example "four" to "a purple elephant"), so they are not exempt; add an exemption if a future check is built differently. Pairs from before this column cannot be backfilled under the immutability trigger, so the migration deactivates them and adds the constraint `NOT VALID`: those retired rows stay unchecked, while every insert and update is checked and they can never be reactivated without a real span. The samples were re-imported as `sample-v1` under new UUIDs.
- After a guess is stored, the reveal also returns `answerReal` and `realSpan`. When the judged item contained the fake (every paired item, and single items shown fake), the reveal shows the real value beside the fabricated one with minimal styling, pending the reveal redesign. Item responses still carry neither field, nor the hallucination type; pairs retired before real spans existed return a null `realSpan` and show no comparison.
- `STUDY_STATUS` is read per request; only the exact value `open` is study mode, and anything else, including unset, is closed free play. The server sets `sessions.is_study` at creation. Closed `/play` skips consent and the profile and says answers will not be used for research, so `consent_given_at` and `age_confirmed` are nullable, and a check constraint requires both for study sessions. Non-study sessions are excluded like pilots from public totals, the leaderboard, exposure balancing, and default exports (`--include-nonstudy` adds them). `is_pilot` and `is_study` stay separate: a pilot in study mode is `is_study` and `is_pilot`. Sessions from before this change default to non-study, as pre-freeze development data.
- The About page describes every fake as a hand-checked, deliberate change to a real answer, matching the single-span dataset rule; it no longer claims natural model mistakes. The `origin` column remains for a future natural subset, which would need this copy revisited.
- Every exported guess carries its item's `position` in the round (1–10, enforced by the schema) next to `is_pilot`, `is_study`, `device_id`, and `device_round_number`, so position and repeat-play effects can be modeled. A query-level test guards these columns, and CI runs the export both with defaults and with `--include-pilot --include-nonstudy`.
- Exports write every integer column (PostgreSQL `int2`, `int4`, `int8`, found from the query's column types) as pandas nullable `Int64`, built from the raw values, so 8 is written as `8`, not `8.0`, and NULL as an empty field. This covers `final_score`, `best_streak`, `ai_knowledge_rating`, `position`, `response_time_ms`, `confidence`, `total_items`, and `device_round_number`, which is an integer again rather than text.
- Dataset v1, stage 1: the schema does not restrict `category`, so v1 reuses the samples' three (`science`, `geography`, `history`). The 40 candidates per type split 14/13/13 so the final 20 can split 7/7/6, and no topic repeats across the whole set. The candidates were written by Claude (`claude-opus-5-5`) from its own knowledge and are only checked, not sourced, against Wikipedia and Crossref.
- Source checks use the rendered text from the MediaWiki `parse` API, including the infobox but excluding footnote markers and reference lists, and record the revision checked so later stages compare against the same text. A code review found that the first version also matched wikitext, footnote numbers and citation metadata, which let small numbers pass vacuously ("130 ships" for the Spanish Armada matched a footnote; the article gives 141, 137 and 122) and wrongly rejected fakes. Those are now excluded, spaced digit groups count as one number, and stage 1 was rerun. Numbers must match as whole numbers apart from thousands separators and units; rounding does not count, so `21,196` fails against `21,196.18`. Crossref checks the DOI's title, the first author's family name, and the year (off by one is flagged). No contact email is sent to Crossref, which keeps requests in its public pool.
- Candidate rows reuse `import_pairs.validate` by completing each row with a placeholder fake, so the importer stays the single source of the pair rules. Format rules add 25 to 60 words, 1 to 3 sentences (initials and abbreviations such as "S." and "St." do not end a sentence) and a hedge-word list in which only lowercase "may" counts, so the month is allowed. Failing candidates are written to `candidates_v1_failed.csv` with reasons; before the recorded run, three drafts with hedge words were reworded.
- The four v1 attention checks are written by hand, one per type (none use `other`), with absurd fabricated spans. Like the samples they are single-span swaps, so they meet the real-span rule. HTTP responses are cached under the ignored `research/dataset_generation/.cache/`.
- Dataset v1, stage 2: fakes come from `microsoft/Phi-3-mini-4k-instruct-gguf` (`Phi-3-mini-4k-instruct-q4.gguf`, SHA-256 `8a83c7fb…2edef`, pinned revision), a family outside the Gemma, Llama and Qwen models evaluated later. It runs on CPU through `llama-cpp-python` 0.3.36 (pinned in `research/requirements.txt`; source-only, so installs compile it) with seed 20261101 reset per candidate, temperature 0.7 and 6 threads, and replies are constrained to a JSON schema. The model file and HTTP cache stay out of Git.
- Number fakes must have exactly the real value's shape (each digit position, separators, decimals and unit), which enforces "same unit, formatting and digit count" mechanically; "round" means ending in 0 with no nonzero decimals. Date fakes must be written in the real date's exact format. Entity fakes must resolve to an unambiguous Wikipedia article whose Wikidata item differs from the real one but shares an instance-of (P31) class, which is how "the same kind of thing" is checked without a hand-made taxonomy. Citation fakes must match the real title's case style, subtitle colon and final punctuation, and Crossref must return no work whose title matches.
- Every fake is also rejected if it already appears in the real answer (which would make the pair ambiguous) or anywhere in the stage 1 revision of the source article. DOI-sourced citations have no article text, so the Crossref check stands in. Length outside 0.7 to 1.3 times the real span is a flag, not a rejection. Each completed pair is validated with `import_pairs.validate`, using the real answer as a placeholder `explanation` until selection writes the final one. Every model reply is logged in `fakes_v1_attempts.csv`, and candidates left with no passing fake go to `fakes_v1_failed.csv`.
- The first stage 2 run used generic per-type rules and kept a fake for only 18 of 35 number candidates and 18 of 40 entity candidates (109 of 153 overall). The rejections were correct but showed the model ignoring the rules: places for people ("Edinburgh" for Alexander Fleming), decimals for whole numbers ("79.000000"), and sentences instead of names. The rules were revised once: number prompts give the exact digit pattern (`#,###`), and entity prompts name the kind from Wikidata ("person", "business or public company"). Date and citation prompts were unchanged. The checks themselves were not loosened. A code review then found two check bugs that had also cost fakes: a thousands group starting with 0 (`,098`) read as a leading zero, and footnote numbers counted as article text. With the revised prompts and fixed checks, 126 of 152 candidates have a fake (28 numbers, 25 entities, 39 dates, 34 citations). The date and citation replies matched the first run exactly, which confirms that seeded generation reproduces.
- Dataset v1, stage 3: the artifact check shows exactly half the fakes first rather than flipping a coin per pair, so pairs with no surface difference (same-shape numbers and dates) score exactly 50% instead of whatever share the coin flips gave. The model has no intercept and the features are not centred, so only the features can predict the fake. Accuracy is pooled over 10 stratified folds with a Wilson 95% interval. scikit-learn is pinned at 1.9.1. On the 126 passing candidates it passes (56.3%, CI 47.6-64.7%), but citation fakes are usually shorter than the real titles (26 of 34) and are detectable on their own (74%). That is left for the hand selection to correct rather than filtered automatically, and the check will be rerun on the final 80.
- Dataset v1, stage 4: `review_v1.csv` lists alternates as fabricated spans, since each replaces `real_span` the same way as the main fake. The script refuses to overwrite a sheet with hand entries. Stage 1 checks only `real_span`, so four subagents fact-checked every other claim in the real answers. Their verdicts are in `claims_v1.csv` and appear as `claim_wrong` or `claim_unverified` flags. They are advisory: nothing is dropped or rewritten because of them, and the hand check decides.
